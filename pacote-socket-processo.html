por dentro do kernel

Entre o pacote e o processo, sempre existe um socket

O processo nunca fala direto com a rede, e a rede nunca fala direto com o processo. Existe sempre um intermediário no meio — o socket (dentro dele, uma struct sock no kernel). É pacote ↔ socket ↔ processo, nunca pacote → processo.

⚠ Isto é uma visualização abstrata e didática, não uma simulação fiel do kernel. Muita coisa real foi deixada de fora de propósito — segmentação/reassemble de TCP, buffers de anel da placa de rede, DMA, IRQ, softirqs, cópias entre espaço de kernel e espaço de usuário, accept() criando um socket novo, controle de congestionamento, etc. O único objetivo aqui é fixar a ideia central: quem recebe o pacote é o socket, não o processo — e o processo só enxerga o que o socket entrega quando ele pede (read/recv) ou manda (write/send).

O pacote carrega 4 números + 1 protocolo — IP origem, porta origem, IP destino, porta destino — mais o corpo que ele transporta. O kernel compara essa 5-tupla com a tabela de sockets abertos: se achar uma ESTABLISHED com tupla idêntica, entrega ali; senão cai numa LISTEN que só olha a porta local. O corpo do pacote fica na fila do socket — não vai para o processo sozinho. O processo só recebe esse conteúdo quando ele mesmo pede, o que a próxima aba mostra. Simplificação: não representamos o three-way handshake, nem a criação de um socket novo via accept() para cada conexão — tratamos o socket ESTABLISHED como se já existisse pronto.

O processo não sabe, por conta própria, que chegou um pacote — ele só tem um file descriptor (fd) que aponta para um socket. Quando chama read(fd, buf, ...), ele está pedindo ao kernel: "copie o que estiver esperando nesse socket para dentro do meu buffer". Antes disso, os bytes ficam só dentro do kernel, na sk_receive_queue — o processo não enxerga IP, porta nem cabeçalho nenhum, só o corpo que sobrou. Simplificação: na vida real read() pode retornar menos bytes do que foi pedido, pode bloquear esperando dado chegar (ou não, se o socket for non-blocking), e a cópia kernel→usuário é uma operação de baixo nível própria — aqui tratamos como um pulo instantâneo e completo.

O caminho é o mesmo, ao contrário. O processo escreve num buffer seu (memória do próprio processo) e chama write(fd, ...). O kernel copia esses bytes para a fila de envio do socket (sk_write_queue), e só depois monta o pacote de verdade — adicionando os cabeçalhos IP/TCP, agora com origem e destino invertidos em relação ao pacote que chegou — para entregar à placa de rede. Simplificação: pulamos segmentação em MSS, cálculo de checksum, controle de janela/congestionamento, ARP, e a fila real do driver da placa de rede — aqui é só "processo escreve → socket guarda → kernel empacota e manda".
